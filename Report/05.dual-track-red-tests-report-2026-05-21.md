## 6. 부록 — GREEN이 존재하는 이유 (Step 05와의 관계)

Step 05는 **RED 전용**이었으나 `ctest`에서 **4/6 PASS**가 나온 이유를 정리한다. “Green”은 (1) TDD 단계 이름, (2) Step 03에서 이미 만든 통과 스위트, (3) Git `green` 브랜치 계획 — 세 가지로 구분한다.

### 6.1 TDD 방법론상 GREEN은 의도된 단계

| 단계 | 의미 |
|------|------|
| **RED** | 테스트가 실패하는 상태 — 요구를 코드로 고정 |
| **GREEN** | 테스트를 **통과시키는 최소 구현**을 넣는 단계 |
| **REFACTOR** | 통과를 유지한 채 구조만 개선 |

GREEN은 결함이 아니라 RED 다음에 **반드시 오는** 단계이다. RED만 있으면 인수(동작 보장)를 확인할 수 없으므로, 프로젝트·README·`.cursorrules` 모두 **RED → GREEN → REFACTOR** 순서를 전제로 한다.

### 6.2 이 저장소에 GREEN 코드가 생긴 시점 — Step 03 (Step 05 이전)

| 항목 | 내용 |
|------|------|
| **커밋** | `d27f863` — `feat(step03): Catch2 BCE skeleton, 36 unit tests` |
| **산출** | `src/entity`, `src/boundary`, `src/data`, `src/main.cpp` + Catch2 36 TEST_CASE |
| **검증** | 당시 `ctest` **4/4 PASS** (Report Step 03) |
| **결함 수정** | `docs/defect_list.md` DEF-001~008 — RED에서 발견된 허브·convertAll·dangling·ROUND 등을 **GREEN 구현**으로 해소 |

열려 있는 `parser_tests.cpp`, `conversion_tests.cpp` 등은 **Step 03 GREEN 묶음**이며, Step 05와 무관하게 계속 통과한다.

### 6.3 Step 05와 GREEN의 공존 관계

```
Step 03: 테스트 + 최소 구현  → 4 스위트 GREEN ✅
Step 05: 신규 RED 12 TC만   → 2 스위트 링크 RED ❌
         (UnitConverter / ConversionUseCase / loadConfig 미구현)
         → ctest: 4 PASS + 2 Not Run = 4/6
```

| 구분 | Step 05에서 한 일 | GREEN 여부 |
|------|-------------------|------------|
| Track A/B RED 12건 | 테스트 + 선언 헤더만 | **RED** (링크 실패) |
| `LengthConversionEngine`, `InputParser` 등 | 변경 없음 | Step 03 **GREEN 유지** |
| `ctest` 4/6 | 기존 4타깃 PASS | Step 03 Green이 잔존 |

**결론:** Step 05가 GREEN을 **새로 만든 것이 아니다.** Step 03 GREEN이 남아 있어 전체 빌드·ctest가 “일부만 Green”으로 보인다. Step 05 RED 12건을 통과시키는 `.cpp` 구현이 들어가면 **그때 추가 GREEN**이 완성된다 (권고 순서: Logic → UI).

### 6.4 Git `green` 브랜치

Step 02 브랜치 전략(Report/02)에는 장기 브랜치 `green`·`refactor` **권장**이 있으나, Step 05 시점 로컬/원격에는 `main`, `red`, `spec`만 존재하고 **`green` 브랜치는 아직 생성되지 않았다.**  
`red`에서 GREEN 완료 후 `green`으로 merge하는 것은 **향후 단계**이며, Step 05 범위 밖이다.
